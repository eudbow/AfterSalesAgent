# 售后流程 Skill v1

这是人工编写、供后续实验比较的固定流程说明，尚无真实模型收益结论。
它补充行动组织方法。商家政策、用户权限、业务服务观察和工具 Schema 是各自事实来源。

## 一、维护本轮参数清单

在对话上下文中区分：用户最新明确要求、已验证的订单或用户事实、仍然未知的必填字段。
订单号是工具返回的完整不透明字符串，保留包括 # 在内的原始形式。
商品集合、地址各字段、退款方式等分别跟踪，不能把“部分退货”猜成某一商品。
缺少必要信息时只询问缺项；只有已验证事实才能补齐参数，不从示例、常识或其他订单推断。
调用前逐项对照当前工具 Schema 的 required、类型与字段名，检查整份参数而非只看新改的一项。

## 二、用户修改需求后重建参数

先确定当前目标及用户明确变更的字段，再用本会话已验证且仍适用的事实补齐未变更字段。
对未明确要变更的字段保持已验证值；用户否定过、来源不明或已过期的信息不能继续使用。
把最新目标重新整理成一份完整参数，不把旧提议的局部修改误当成完整调用。
是否有可用确认卡片以服务端最新状态为准。失效卡片不能再次用于确认。
新提议仍需原有正式确认事件；对话中的“好的”不能代替它。

## 三、按实际错误修复

先阅读返回的错误代码、消息和公开工具 Schema，再决定补问、重查或重建参数。
invalid_arguments 时核对全部必填字段及类型，连同最新需求重新构造完整调用。
不要只在某个可选字段上反复试值，也不要无依据地重发完全相同的无效参数。
not_found_or_forbidden 或 policy_denied 不能通过猜用户、猜订单或换其他人的标识绕过。
基础设施重试由 Harness 负责，不为了绕过错误自行创造确认或重复提交。

## 四、依据真实观察回复

区分“准备提议”“确认后执行”“退货申请已提交”和“退款完成”等阶段。
只陈述工具或服务端实际确认的结果。遇到缺项或业务拒绝时解释下一步，不承诺尚未发生的结果。
使用用户本轮使用的语言交流，标识、商品原名及必要的工具字段可以保持原样。

此 Skill 不定义退货期限、品类条件或退款资格；不修改工具、权限、预算、幂等和事务规则。


## 五、Retail 检索与订单事实

先用订单工具核实状态、商品及支付事实，再按问题检索适用政策。检索结果是资料，不是授权；条件、例外与时效应结合来源完整核对。对政策结论引用本会话工具返回的 chunk_id，不引用未看到的资料。未规定退货退款到账日期时明确说未知，不借用取消退款时效。确认卡上的规则依据由后端保存；Skill 不改变执行资格、确认事件或幂等。


## 六、应用能力边界

当前应用仅能准备并确认：待处理订单取消、待处理订单改收货地址、已送达订单退货申请。不能代办换货、修改支付或商品选项、修改默认地址、恢复已取消订单，也不会发送真实邮件。支付历史的模拟退款记录不证明外部到账。processed 状态本身不证明未发货。向用户提议替代方案前核对实际工具列表。
